# 项目交接记录 / Project history

这份文档记录本项目从需求到 2.1 版的决策过程、踩过的坑和验证结论。
代码里看不出"为什么这么做"的地方，答案基本都在这里。
（`CLAUDE.md` 讲怎么开发，这份讲为什么这样设计。）

---

## 一、背景和目标

Odoo 19 社区版没有仓库扫码应用（企业版的 `stock_barcode`）。目标是在社区版上做出对标企业版的扫码出入库能力，并接入现有的销售、采购、POS 流程。

**硬约束**：企业版代码是 OEEL 授权，不能拷贝或改写。本项目全部自研，LGPL-3。

**需求确认过的范围**（用户逐项选定）：

- 结算场景：POS 收银、销售单扫码开单加开票、采购收货后对账，三者都要
- 第一期范围：扫码建档、扫码出入库、盘点，全部一起做
- 对标程度：含批次、包裹、GS1 等高级功能
- 设备：手机（安卓和 iPhone）、电脑摄像头、扫码枪混用
- 条码：厂家 EAN/UPC 和自编码并存
- 未知码自动带出商品信息：**不需要**（不接第三方条码 API），手动录入
- 仓库结构：多仓库、多库位、多格
- 标签：POS 机通用热敏标签，按 40×30mm 实现

## 二、社区版源码核实结论（做方案时逐条确认过）

这些结论决定了架构，后续改动前建议复核：

1. **摄像头扫码组件社区版已有**：`web/static/src/core/barcode/` 提供 `BarcodeVideoScanner`、`scanBarcode()`、ZXing 回退。不需要引第三方库。
2. **POS 已自带摄像头扫码**（所有设备）、本地没有的商品会到服务器查、菜单里有新建商品。所以 POS 模块只补了"未知码当场建档并加入订单"。
3. **GS1 解析在社区版**：`barcodes_gs1_nomenclature` 可直接用。
4. **批量/波次调拨在社区版**：`stock_picking_batch`，可以直接在它上面做扫码。
5. **`barcodes` 模块的 `barcode_events_mixin` + `barcode_handler` 控件**：销售单、采购单扫码加行用的就是它，扫码枪和摄像头同路径。
6. **Odoo 17 以后移库明细没有"已完成数量"字段**：所以自建了已扫数量（先是字段，2.0 起改为事件）。
7. **作业类型有 barcode 字段**；库位默认条码是全路径名。
8. **默认条码规则占用了这些前缀**：21 称重、22 折扣、23 价格、10 批次。所以店内码只能用 20 或 24–29，**不是最初以为的 20–29**。也因此扫码引擎不能只靠规则判断类型，必须依次查商品、包装、库位、批次、包裹、单据。

## 三、关键设计决策

### 1. 扫码逻辑放服务器端

条码解析、行匹配、规则校验、状态构建全在 Python，每次扫码返回完整状态，前端只渲染。
**理由**：核心逻辑能被自动化测试覆盖，前端轻、不易出错。代价是每次扫码一次网络往返（实测中位 18 毫秒，可接受）。

### 2. 数量用"扫码事件"，不改共享数据行（2.0 的核心改动）

1.x 时每次扫码都更新同一批 `stock.move.line`，6 人同扫一张单约 5% 的扫码因数据库行锁冲突被拒。
2.0 改为每次扫码新增一条 `stock.barcode.scan.event`，已扫数量由事件汇总；验证时才写入 Odoo 标准字段。

**踩坑记录**：第一版改完并发失败率反而升到约 50%。原因是把已扫数量做成"带写回的计算字段"后，ORM 每次写入仍会更新该行的 `write_date`，大家照样抢同一行。改成完全不碰该行（`line._bc_add(delta)` 只插事件）后才降为零冲突。
**所以：扫码热路径上永远不要写共享行。**

实测：10 人同扫一张单各 30 次，300 次全部成功、零重试。

### 3. 幂等扫码

每次扫码带客户端生成的唯一编号，服务器按编号去重（`stock.barcode.scan.log.client_uuid` 唯一索引）。
这是离线补传敢做的前提：网络中断后重发同一条不会重复计数。

### 4. 离线暂存只覆盖"当前打开的单据"

用户在两种方案里选的这一种（另一种是提前下载任务清单）。扫码先存在浏览器里按序补传；验证、装包、加商品在离线时禁用；补传被拒的扫码集中列出，不静默丢弃。
盘点界面仍需在线。

### 5. 实时刷新走 Odoo bus

别人扫同一张单，本机约 0.3 秒自动刷新，并显示"某某也在处理这张单"（最近 2 分钟有扫码的人）。
推送内容只有单据 id 和用户名，**不含数量等业务数据**。
前提是 `workers>0` 且反向代理开了 WebSocket（用户环境满足）；不满足时自动退回定时刷新。

### 6. 扫码员权限模型

扫码员（`group_barcode_operator`）不给库存后台权限，只有读权限；引擎入口 `bc_guard()` 先做读权限检查（含记录规则，多公司隔离有效），再以 sudo 运行。
**用 `sudo()` 而不是切换用户**：`sudo()` 保留真实 uid，所以 `create_uid`、消息记录和扫码日志上仍是本人。

由此带来一条设计规则：**扫码员打不开后台向导**。所以欠单确认、过期批次确认都改成由扫码界面自己询问；未知码建档改成"提交建档申请"。新增功能时要沿用这个原则。

### 7. 验证始终走 Odoo 标准流程

已扫数量写回 `quantity` + `picked`，然后调用标准 `button_validate()` / `action_done()`。
好处是欠单、上架规则、预留、计价、会计凭证全部由 Odoo 原生处理，不会算错账。已用三步收货、两步发货、退货、FIFO 计价的测试验证过。

### 8. 标签打印用"本地代理"而不是浏览器直连

Odoo 在云上，标签机在仓库局域网，云端连不到。浏览器直连（WebUSB）iPhone 不支持。
最终方案：仓库内任一台电脑跑一个只用标准库的小程序，**主动**连 Odoo 取任务再发给打印机。仓库路由器不用开端口，手机也能触发打印。
文字在服务器端渲染成位图（所以打印机没有中文字库也能打中文），条码用打印机原生指令（更清晰、可扫）。

### 9. 标签用 PDF 还是原生指令

两条都保留：没有配置打印机时退回 PDF（浏览器打印），配置了就直连。

## 四、测试中发现并修复的问题（值得记住）

1. **社区版标签模板中文乱码**：标签 PDF 不经过标准布局时没有字符集声明，中文变乱码。解决办法是把标签包在 `article` 容器里，让 Odoo 套用带字符集的最小布局。
2. **标签尺寸依赖 wkhtmltopdf 版本**：普通发行版自带的版本排版比例是错的，必须用 `0.12.6.1 (patched qt)`（Odoo 官方镜像自带）。
3. **防重复扫码差点误杀**：最初 600 毫秒内同码去重，会吞掉快速连扫同一件商品。改成只去掉"摄像头和扫码枪同时读到同一个码"的跨设备重复，同设备连扫全部计数。
4. **POS 当场建商品需要商品管理员权限**：普通 POS 经理不行，Odoo 的商品创建权限属于"商品/管理员"组。
5. **Odoo 19 的接口默认只读**：给代理用的接口要显式声明可写。
6. **服务器上有多个数据库时**，外部程序调接口要带数据库名（代理脚本的 `--db` 参数）。
7. **报表 action 和模板不能同 id**：同名会报"模型不符"。

## 五、验证结论（截至 2.1）

- 自有测试 **83 项全部通过**，其中 11 项在真实浏览器中操作。
- **Odoo 自带库存测试 639 项**：装与不装本套件结果完全一致（5 项失败是 Odoo 自身在装了采购模块时的已知表现），即未引入原生功能回归。
- 性能：1 万商品、300 行单据，每次扫码服务器端中位 18 毫秒、90 分位 19 毫秒；整单状态 13 毫秒；300 行整单验证 0.5 秒。
- 并发：10 人 × 30 次同扫一单，零冲突、数量准确。
- 升级：1.0 → 1.1 → 2.0 → 2.1 带数据升级验证通过（2.0 迁移实测 23 行、合计 134 件，前后一致）。
- 标签直连：真实 Odoo → 真实代理程序 → 模拟网口标签机，收到完整 TSPL 指令，任务状态转为已打印；指令还原成图片核对过排版。

**沙箱验证不了、需真机确认的**：摄像头实际取景、各品牌扫码枪、标签机实际出纸效果（特别是 TSPL 位图黑白方向，打反了在打印机配置里勾"反转文字位图"）。

## 六、生产环境事实

- Odoo 19 社区版，Docker 部署，addons 在 `/opt/prod-apps/odoo/addons`，容器内 `/mnt/extra-addons`
- 生产数据库 `letaoge`，另有 staging
- 反向代理是 Nginx Proxy Manager，HTTPS 已就绪（摄像头必需），WebSocket 已开，`workers>0`
- 交付习惯：**一个部署脚本 + 一个模块包，两个文件**，不用其他形式
- 部署脚本 `scripts/deploy-barcode-ce.sh` 会自检容器、addons 目录、wkhtmltopdf 版本、Pillow、workers 配置，并备份模块目录、打印回滚命令；**数据库不自动备份**

## 七、当前未做的事

模块内：

- 生产（MRP）扫码、质检扫码
- IoT 盒子直连打印、自动称重
- 货主（寄售）库存、套件商品（BOM kit）
- 离线暂存只覆盖出入库，不含盘点
- 扫码规则只能按作业类型配，没有全局策略页
- 多步路线的连续扫码走的是 Odoo 原生链路，已有测试，但真实多步仓库未实跑

下一阶段（独立项目，不在本仓库）：

拍箱规 AI 录入（拍一张箱子照片，模型填出"单品→中包→箱→托"的包装层级和数量）、装箱单识别与应到实到对比、唯一箱码打印、任意时间段按数量金额和往来账对账、自然语言查询、低库存提醒。
架构上定的是**独立核心服务 + Odoo 薄适配层**：业务逻辑在独立服务，Odoo 这边只做适配，避免两边重复。
`stock.barcode.scan.event` 和 `stock.barcode.scan.log` 就是为它准备的数据源，因此这两张表**只允许追加**，并带 `schema_version` 版本号。
